# 13 — Known Failures and Rebuild Guardrails

Purpose: preserve lessons from defects observed during development so a clean rewrite does not reintroduce them.

These are historical failure modes. Inclusion here does **not** assert that each defect still exists at the documentation snapshot.

## KF-01 — Fixed ~101 km/h pace lock

### Symptom
Cars could become attracted to approximately 101 km/h / 28 m/s, making race speed mechanical and uniform.

### Historical cause class
A fixed formation/pace target leaked into active race behaviour or overrode physical speed planning.

### Guardrail
- no unexplained fixed normal-race target speed;
- all caps identify their source/reason;
- speed-variety regression retained;
- direct velocity assignment outside physics/service/recovery reviewed as critical.

## KF-02 — Faster car follows instead of overtaking

### Symptom
Even with adequate track width and performance advantage, a follower remained behind a slower car.

### Cause class
Collision/follow safety treated “car ahead” as sufficient reason to cap speed and never created/recognized a safe pass escape trajectory.

### Guardrail
- pass intent creates a predicted lateral escape before follow cap dominates;
- available left/right corridor explicitly evaluated;
- wide-straight deterministic pass test;
- multiclass pass test.

## KF-03 — Side-by-side car slows and gives up pass

### Symptom
A car already alongside slowed despite having a safe parallel path.

### Cause class
Proximity/longitudinal overlap was confused with future collision convergence.

### Guardrail
- predictive collision model distinguishes safe parallel from convergence;
- no automatic braking from overlap alone;
- parallel side-by-side regression.

## KF-04 — Excessive collisions / chaotic racing

### Symptom
Cars hit one another frequently; race looked disorganized rather than competitive.

### Cause class
Conflicting lane writers, insufficient future prediction, unstable commitment and/or physical contact immediately overwritten by trajectory logic.

### Guardrail
- one lateral authority;
- explicit tactical commitment/hysteresis;
- predicted path/TTC safety;
- physical contact has authoritative post-impact state;
- chain-incident stability tests.

## KF-05 — Pit entry “suction” / late lateral jump

### Symptom
Pit-bound car was unnaturally pulled sideways toward pit lane, sometimes at high speed.

### Cause class
Pit strategy/state switched to entry geometry before the vehicle had physically reached the entry blend.

### Guardrail
- first-class `PIT_APPROACH` phase;
- early request remains on track;
- approach trajectory begins early and is bounded by lateral acceleration/jerk;
- early-entry regression.

## KF-06 — Impossible pit-entry deceleration

### Symptom
Car could enter pit lane at an implausible rate, losing speed nearly instantaneously.

### Cause class
Legacy limiter/speed clamp directly overwrote velocity instead of braking toward the control line.

### Guardrail
- limiter is control constraint, not teleport in velocity space;
- brake-distance planning;
- per-frame acceleration/deceleration discontinuity checks.

## KF-07 — Pit exit warp

### Symptom
Car appeared to jump from pit lane back onto the racing surface.

### Cause class
Exit state handed directly to normal track/racing-line position rather than following a merge corridor.

### Guardrail
- `FAST_LANE_EXIT` and `MERGE` are physical phases;
- limiter/end line explicitly represented;
- continuous pose/speed/heading acceptance test;
- normal racecraft resumes only after merge completion.

## KF-08 — Pit lane blocked by service car

### Symptom
One stopped car could prevent cars behind from passing through the pit lane.

### Cause class
Fast lane and working/service lane were not physically separated enough or service pose occupied passage space.

### Guardrail
- explicit fast + working lane geometry;
- team boxes align outside fast lane;
- fast-lane passage scenario while another car is serviced.

## KF-09 — One-at-a-time global pit service

### Symptom
Pit operation appeared serialized even across different teams.

### Cause class
Service occupancy modeled globally rather than per team/box.

### Guardrail
- per-team box ownership;
- parallel different-team service test;
- same-team double stack separate queue logic.

## KF-10 — `BOX THIS LAP` radio spam

### Symptom
Identical pit instruction repeated continuously.

### Cause class
Radio triggered from per-frame state rather than state transition/event identity.

### Guardrail
- semantic event keys/deduplication;
- radio generated by transitions;
- repeat-frequency regression.

## KF-11 — Objects on track / pit-entry obstruction

### Symptom
Decorative/collision objects appeared on the racing surface or at pit entry.

### Cause class
World decoration lacked corridor exclusion or duplicate obsolete geometry remained active.

### Guardrail
- authoritative driveable corridor exported to world-placement validation;
- no scenery collider inside corridor unless explicitly whitelisted;
- build only one final barrier/world set;
- automated geometry clearance audit.

## KF-12 — Jagged grass/runoff overlaps road

### Symptom
Grass edge looked sawtoothed and sometimes encroached on the circuit.

### Cause class
Independent/coarse edge geometry did not follow the final road boundary smoothly.

### Guardrail
- derive runoff/grass boundary from authoritative track edge;
- continuity/tessellation threshold;
- visual validation at representative corners.

## KF-13 — Weak class differentiation

### Symptom
Formula/Hyper/Prototype/etc. could look too similar in maximum speed or overall performance.

### Cause class
Class identity overemphasized a single top-speed number or race logic suppressed physical differences.

### Guardrail
- class differences span acceleration, braking, tyres, aero, mass, traction and strategy;
- low/medium/high-speed comparative tests;
- multiclass closing/pass tests;
- no common traffic cap that erases class performance except genuine safety/rules.

## KF-14 — Unrealistic corner speed / mechanical slowing

### Symptom
Cornering could be too fast, or later fixes could risk substituting arbitrary speed reductions.

### Guardrail
- corner speed derived from curvature + physical tyre/aero envelope;
- look-ahead braking;
- friction-circle validation;
- no per-corner “subtract X km/h” patch.

## KF-15 — Waypoint attraction / diagonal driving / steering snaps

### Symptom
Cars could point diagonally, chase points mechanically or make abrupt steering corrections.

### Cause class
Direct waypoint target control without continuous trajectory/steering-rate dynamics.

### Guardrail
- target path is continuous;
- bounded steering angle/rate and lateral jerk;
- ideal line is reference, not position constraint;
- no direct transform-to-waypoint movement.

## KF-16 — Track segments overlap / circuit becomes tangled

### Symptom
Road geometry crossed/overlapped unintentionally and made the circuit visually incoherent.

### Guardrail
- authoritative track spline self-intersection audit;
- road-surface overlap detection;
- intentional crossing requires elevation separation metadata;
- no decorative road duplicate.

## KF-17 — Spin rate / incident behaviour feels artificial

### Symptom
Spins may become too frequent or appear as random events detached from driving.

### Guardrail
- mistakes act on causes/inputs/grip, not direct “spin now” result where avoidable;
- incident frequency calibrated from long-run scenario statistics;
- driver traits alter risk/precision rather than outcome assignment.

## KF-18 — Immediate pit stop at race start without credible reason

### Symptom
Cars could pit immediately after the race begins.

### Cause class
Strategy state, initial wear/fuel/damage or pit trigger initialization could be invalid.

### Guardrail
- validate starting fuel/tyres/damage;
- strategy emits reason-coded pit request;
- start-window pit decisions require a valid reason (damage/weather/rule/etc.);
- deterministic start strategy test.

## KF-19 — Qualifying code persists after feature removal

### Symptom/risk
Removed feature can survive as dead branches/state and later interfere with session logic.

### Guardrail
- clean build contains no qualifying state/data/transitions;
- explicit no-qualifying source/runtime test.

## KF-20 — iPhone UI renders but controls do not work

### Symptom
Screen can appear running while buttons/camera controls are unresponsive or scene is effectively static.

### Cause class
Touch/pointer handling, overlay interception, render/runtime initialization or mobile compatibility failure.

### Guardrail
- iPhone/WebKit interaction tests click/tap real controls;
- test state changes, not only presence of DOM elements;
- verify moving simulation and camera changes.

## KF-21 — Duplicate controllers “repair” one another

### Symptom
A fix in one layer is overwritten by another; more corrective layers accumulate, making behaviour unpredictable.

### Guardrail
This is the most important architectural guardrail:

> Never add a second writer to compensate for the current authoritative writer.

When behaviour is wrong, fix the owner. Arbitration combines **requests/constraints** before the owner applies motion; it does not run a second corrective motion system afterward.

## KF-22 — Symptom patching instead of root-cause repair

### Prohibited patch patterns

- coordinate warp;
- fixed emergency pace without physical reason;
- arbitrary slowdown because another car exists;
- enlarged collision gap until overtakes disappear;
- hidden teleport into/out of pits;
- acceptance threshold weakened merely to pass test;
- visual-only repositioning that hides physical state mismatch.

### Required workflow

`reproduce -> identify owner -> root cause -> minimal architectural fix -> targeted test -> adjacent regression -> document decision`

## Final guardrail

A visually smooth result is not sufficient if the underlying authority is wrong. The rebuild should prefer one explainable physical chain over many corrective layers that happen to look acceptable in one scenario.
