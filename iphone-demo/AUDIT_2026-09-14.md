# Racing iPhone Runtime Audit — 2026-09-14

## Scope

This audit covers the active browser game path under `iphone-demo/`, especially:

- `app.js`
- `runtime/*`
- active legacy providers reached through `runtime/index.js`
- rendering, camera, environment, pit flow, profiling and mobile performance
- repository architecture/testing documents where they directly affect the active game

## Executive summary

The game now has broad simulation, weather, race-control, camera, audio and pit functionality, but the active browser build still depends on a deep historical `vNN-*` provider chain. The largest product-quality risk is no longer missing features; it is **ownership fragmentation**: the same subsystem can be modified by several generations of wrappers.

The recent pit queue regression is a concrete example. Pit admission exists in `v30-race.js`, box travel/service correction exists in `v41-race.js`, and runtime double-stack behaviour exists in `runtime/race.js`. Each layer is locally reasonable, but together they can create invalid state transitions.

Graphically, the vehicle materials are already stronger than the overall image. The largest visible gaps are grounding, surface detail, environment/reflection consistency, shadow allocation and asset fidelity.

## Changes implemented in this audit

A new stable `runtime/visuals.js` layer was added and activated from `app.js`.

Implemented visual improvements:

1. 4x anisotropic texture filtering on mobile, up to 8x on desktop.
2. Two rubbered tyre paths following the computed optimal racing line.
3. Instanced braking rubber traces in heavy braking zones.
4. Lightweight per-car contact shadows to reduce the floating-car look.
5. Wet-road roughness / reflection response tied to runtime wetness and rain.
6. Rain-dependent atmospheric visibility/fog distance.
7. Emissive practical lighting at the aligned pit garage entrances.
8. Directional-shadow projection tightened from the original very large coverage area.
9. New stable `runtime/camera.js` wrapper keeps the sun/shadow volume centred on the current broadcast subject instead of always on the race leader.

The implementation deliberately avoids heavy mobile post-processing such as SSAO, volumetric fog and full-screen bloom.

## Findings by priority

### P1 — High priority

#### 1. Pit logic ownership is fragmented across multiple layers

Current ownership is split across at least:

- `v30-race.js`: pit admission / traffic / team-box avoidance
- `v41-race.js`: travel-to-own-box correction and service start
- `runtime/race.js`: working-lane queue, double-stack and service failsafe

This creates order-dependent behaviour and makes regressions difficult to reason about.

**Recommendation:** move the full pit state machine into one stable runtime module with explicit states such as `TRACK`, `PIT_ENTRY`, `FAST_LANE`, `WORKING_APPROACH`, `QUEUE`, `SERVICE`, `WORKING_EXIT`, `FAST_LANE_EXIT`, `MERGE`. Legacy providers should emit strategy intent only, not mutate pit movement states.

#### 2. Browser runtime still depends heavily on historical `vNN-*` modules

`runtime/index.js` is now the application facade, which is good, but director, environment, safety-car, broadcast, performance/settings/circuit providers and large parts of world/race still delegate to historical modules.

**Recommendation:** flatten one subsystem at a time only after adding behavioural regression tests. Start with pit/race-state ownership because it is currently producing real bugs.

#### 3. Architecture documentation is materially stale

`ARCHITECTURE.md` still describes the project as Phase 0 / implementation not started and describes the intended Rust headless simulation architecture. The active iPhone game is a mature JavaScript/Three.js runtime with a compatibility-provider chain.

**Recommendation:** split documentation into:

- `ARCHITECTURE_TARGET.md` — desired Rust/headless end state
- `ARCHITECTURE_RUNTIME.md` — actual current browser architecture

Do not label the target design as the current architecture.

#### 4. Browser/visual regression validation is manual

`TESTING.md` has strong acceptance criteria, but visual validation is explicitly a manual checklist. There is no browser-level automated regression protecting pit state transitions, camera composition or rendering output.

**Recommendation:** add deterministic Playwright-style browser scenarios and screenshot baselines for at least:

- sunny race start
- heavy rain
- dusk/night lighting
- multi-team pit stop
- same-team double stack
- pit entry and exit merge
- multi-car incident / recovery

Record profiler metrics and fail the test if draw calls, frame time or pit state invariants exceed thresholds.

#### 5. World construction still creates obsolete geometry that runtime later hides

The stable runtime currently builds on v42 and hides obsolete pit ribbons/doors/boxes rather than preventing their construction.

**Recommendation:** extract a clean `world-core.js` that constructs only active geometry. This reduces startup cost, memory churn and future geometry-selection hacks based on dimensions/materials.

### P2 — Medium priority

#### 6. Dynamic sky and vehicle reflection environment are not fully coupled

The dynamic sky is shader-driven, while physical vehicle materials inherit the older environment source. At sunset/night/rain, direct lighting changes but body reflections can remain perceptually disconnected from the sky.

**Recommendation:** provide a small set of prefiltered PMREM environments (day, overcast, sunset, night, wet) and blend/switch by sky state. Avoid regenerating PMREM every frame on mobile.

#### 7. Procedural geometry is now the primary graphical ceiling

Cars use layered procedural primitives and good physical materials, but the silhouette, panel detail, lights, wheel/brake assemblies, pit buildings, trees and track furniture remain visibly synthetic at close range.

**Recommendation:** migrate visual-only assets to optimized GLB/GLTF with:

- LOD0/LOD1/LOD2
- KTX2/Basis textures
- compressed normal/roughness maps
- instancing for track furniture
- generic/non-licensed racing vehicle designs

Keep simulation collision dimensions independent of render meshes.

#### 8. Track surface texture resolution is low for close broadcast shots

The base asphalt/bump textures are generated at 256x256. Anisotropy improves oblique clarity, but cannot create missing micro-detail.

**Recommendation:** move to 512–1024 compressed tiling textures with independent albedo, normal and roughness channels. Retain procedural variation to avoid obvious repetition.

#### 9. Shadow quality is still single-volume directional shadowing

The new runtime improvement allocates the existing shadow volume to the current broadcast subject, which materially improves useful resolution. It is still one shadow map and therefore a compromise for very wide shots.

**Recommendation:** keep the current solution for mobile. On desktop/QUALITY only, evaluate two-cascade directional shadows or a second small near-subject shadow map if GPU budget allows.

#### 10. Quality adaptation mostly changes cadence/DPR, not scene complexity

The current performance manager smartly reduces background update rates first, but scene draw-call/geometry complexity is not strongly tiered by quality level.

**Recommendation:** expose a runtime quality callback so visual systems can reduce:

- contact-shadow distance
- crowd/track-furniture density
- garage detail
- spray/debris counts
- high-detail vehicle parts

before lowering render scale.

#### 11. Three.js is a remote CDN runtime dependency

The browser entry point imports Three.js directly from jsDelivr. A CDN/network failure prevents the game from starting even when the rest of the project is available.

**Recommendation:** vendor the pinned Three.js build or add a local/fallback source for production hosting.

### P3 — Lower priority / polish

#### 12. Pit broadcast camera variety is limited

The pit shot is essentially a static pit-wall-side camera. With the new fast/working-lane separation, pit sequences now deserve better coverage.

**Recommendation:** add three pit-specific broadcast shots: garage-front three-quarter, pit-wall telephoto and overhead/gantry. Cut only on stable state boundaries to avoid camera jitter.

#### 13. Selective post-processing could improve desktop presentation

The current image has no dedicated selective bloom or screen-space ambient treatment.

**Recommendation:** do not enable heavy post effects globally on iPhone. Consider optional QUALITY-only selective bloom for brake lights/pit lights and a lightweight FXAA/SMAA fallback where MSAA is insufficient.

#### 14. Profiling is strong but visual quality metadata should be recorded

The runtime profiler already records FPS, CPU/GPU time, DPR, draw calls, triangles and quality level.

**Recommendation:** include visual-enhancement state in diagnostic payloads (anisotropy, contact-shadow range, wet-road mode, shadow projection size) so screenshots/performance reports can be reproduced exactly.

## Recommended execution order

1. Consolidate pit state ownership and add deterministic pit regression tests.
2. Add browser scenario/screenshot automation.
3. Flatten `world-core` and stop constructing hidden legacy geometry.
4. Introduce optimized GLB vehicle/trackside assets with LOD and compressed PBR textures.
5. Couple sky/weather with prefiltered environment reflections.
6. Add quality-tier scene complexity controls.
7. Add desktop-only selective post-processing after measuring GPU budget.

## Current visual target

For the browser/iPhone version, the best quality strategy is not to chase console/PC-style full post-processing. The highest return per millisecond is:

- better assets/material maps
- sharp useful shadows around the broadcast subject
- strong contact/grounding cues
- surface variation and rubber/wetness
- believable lighting transitions
- high-quality camera composition

That keeps the spectator-game presentation substantially more realistic while respecting mobile thermal limits.
