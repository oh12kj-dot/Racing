# assets/tracks — トラック定義

## 形式

JSON。スキーマバージョンは `sim_track::TRACK_SCHEMA_VERSION`（現在 **1**）。
破壊的変更のたびに上げること。読み込み時にバージョンが検証され、
不一致なら `TrackIoError::UnsupportedVersion` になる。

**なぜ JSON か（RON ではなく）**: このデータは Rust の Simulation Core だけでなく、
**Blender Python**（車両・トラックサイド生成）と **Engineering View**（JavaScript）も読む。
3 つの言語すべてが追加ライブラリなしで読める形式である必要がある（DECISIONS.md ADR-0006）。

## 読み込み

```rust
use sim_track::load_track;
let track = load_track("assets/tracks/aoyama_ring.track.json")?;
```

読み込みは **その場で `Track::build` を実行して検証する**。
幅が 0 以下、断面数の不一致、セクター境界の不正などは
`TrackIoError::Invalid` として弾かれ、不正なデータが後段のシステムへ流れることはない。

## 座標規約（変更禁止）

- 右手系、**`+Y` が上**
- 水平面は XZ
- 進行方向に対して **左が `+t`（横方向オフセット正）**
- 角度はすべてラジアン、長さはすべてメートル（SI）

## フィールド

```jsonc
{
  "schema_version": 1,
  "description": "任意の説明文。シミュレーションからは参照しない",
  "track": {
    "name": "Aoyama Ring",
    "centerline": [ {"x": 0.0, "y": 0.0, "z": 0.0}, ... ],
    "sections":   [ { ... }, ... ],
    "closed": true,
    "sector_splits": [0.34, 0.68],
    "start_finish": 0.0
  }
}
```

| フィールド | 単位 | 意味 |
|-----------|------|------|
| `centerline` | m | センターラインの制御点。`y` が標高。**間隔は半径から決める**（下記「制御点間隔について」）|
| `sections` | — | 各制御点の断面。**`centerline` と同数でなければならない** |
| `closed` | — | サーキットは常に `true` |
| `sector_splits` | 割合 | 全長に対する比。昇順・`(0,1)` の範囲。要素 2 で 3 セクター |
| `start_finish` | 割合 | スタート/フィニッシュラインの位置。`[0,1)` |

### `sections` の各要素

省略した項目は `CrossSection::default()` の値になる（`{}` だけでもよい）。

| フィールド | 単位 | 意味 |
|-----------|------|------|
| `width_left` / `width_right` | m | センターラインから白線までの距離。**正**であること |
| `banking` | rad | 路面の横断傾斜。**正で左端が持ち上がる**。物理的に正しい向きは「外側が高い」なので、左旋回では**負**、右旋回では正にする |
| `camber` | rad | **現在データとして保持のみで、幾何には未適用**。下流はこれを前提にしないこと |
| `kerb_left` / `kerb_right` | m | 白線の外側に続く縁石の幅。`0` なら縁石なし |
| `runoff` | — | 縁石の外側の路面。`"asphalt"` / `"kerb"` / `"grass"` / `"gravel"` / `"pit_lane"`（snake_case） |

## 制御点間隔について（重要）

規約は 2 つある。**どちらもテストで機械的に検証している**
（`crates/sim-track/tests/io.rs`）。

### 規約 1 — 間隔は半径から決める（`chord / R <= 0.25`）

centripetal Catmull-Rom は **円弧を厳密には再現しない**。
逸脱はおおむね `(chord / R)^2` に比例するため、曲率リップルを決めるのは
間隔の絶対値ではなく **半径に対する比**である。

| 半径 | 上限間隔 |
|------|---------|
| R | **`0.25 * R`** |
| 直線 | 20 m（絶対上限） |

一律の下限（かつて「8〜20 m」としていた）では小半径コーナーを守れない。
実測例: ヘアピン（R=19 m）を 9.83 m 間隔（`chord/R = 0.52`）で置いたところ、
曲率が **周期 10.5 m で ±13% 振動**した（R が 16.3 ↔ 21.0 m で往復）。
4.51 m 間隔（`chord/R = 0.24`）へ詰めて **±2.7% に収まった**。

高速コーナーは半径が大きく `chord/R` が自然に小さいため、
10 m 間隔でも 0.8% しか振れない。**壊れるのは小半径コーナーだけ**である。

### 規約 2 — 密度を急に変えない（隣接間隔比 <= 1.5）

密度が急変すると接線の推定が跳ね、その継ぎ目に曲率のオーバーシュートが生じる。

実測例: 円弧を 10 m 間隔、直線を 18 m 間隔で置いたところ、
半径 130 m のコーナーの出口に **半径 101 m 相当の 1 サンプル分のスパイク**が出た。
直線側の間隔を継ぎ目で 10 m、中央で 18 m へ滑らかに変化させることで解消している。

コーナーを詰めたら、**隣接する直線側にも間隔のランプを作ること**。
`tools/tracks/densify_corners.py` がこれを自動で行う。

### なぜ重要か

これは見た目の問題ではない。Phase 2 の Speed Profile は曲率から限界速度
`v = sqrt(mu*g*R)` を計算するため、偽のリップルやスパイクは
**偽のスロットル／ブレーキ脈動**になる。

**半径を中央値で測る検査は、リップルを素通しする。**
中央値は半径の測定には正しく、滑らかさの測定にはならない。
平滑性は `aoyama_curvature_has_no_ripple` など専用のテストで検証すること。

### 既知の特性 — 弧と直線の継ぎ目

このトラックは緩和曲線（クロソイド）を持たず、円弧と直線が直接つながる。
曲率は設計上そこで不連続に変化し、Catmull-Rom はその段差でオーバーシュートする。
実測では全 9 コーナーで一様に `median_R / min_R = 1.41〜1.51` である
（ヘアピンだけが悪いのではない）。

平滑性テストはこの継ぎ目を対象から外している（両端 12 m を落とす）。
そこを平坦にするには全コーナーに緩和曲線を入れる必要があり、
それはトラックの設計変更にあたる。

## 同梱トラック

### `aoyama_ring.track.json` — Aoyama Ring

**オリジナルのサーキットである。実在のレーストラックを模していない。**
名称・レイアウト・コーナー名はすべて架空であり、実在チーム・ドライバー・
スポンサー・サーキットの名称や意匠を含まない（DECISIONS.md ADR-0006 IP Policy）。

実測値（`cargo test --release --test io` で機械的に検証している）:

| 項目 | 実測 |
|------|------|
| 全長 | 4 139 m |
| 制御点 | 337（間隔 4.51〜18.15 m、最大 `chord/R` = 0.238） |
| 最長ストレート | 742 m |
| 高速コーナー（R >= 120 m） | 4（130 / 150 / 185 / 140 m） |
| 中速コーナー（R 40〜80 m） | 5（62 / 58 / 52 / 79 / 45 m） |
| ヘアピン | 1（R 19.2 m、旋回 150 度） |
| S 字 | 1（コーナー間 66 m の逆向き 2 連） |
| 高低差 | 23.5 m（登り・下りの両方） |
| バンク | T7 に -0.100 rad（左旋回なので外側 = 右が持ち上がる） |
| コース幅 | 12.0〜16.0 m |
| セクター | 3 |
| ファイルサイズ | 79.6 KB |

コーナー半径は**設計値ではなく `Track::frame_at(s).curvature` の実測の中央値**で
検証している。継ぎ目の 1 サンプル分のスパイクに引きずられないため。

## 新しいトラックを追加する手順

1. `<name>.track.json` を作る。上記のフィールドと制御点間隔の規約に従う
2. `sim_track::load_track` で読めることを確認する（構築時検証が走る）
3. `crates/sim-track/tests/io.rs` の `asset_track_meets_layout_requirements` に相当する
   検証を追加し、**レイアウト要件を数値で確認する**。目視で済ませない
4. 自己交差がないことを確認する（離れた `s` どうしの水平距離がコース幅より大きいこと）
5. 実在サーキットを模していないこと、IP に触れないことを確認する

## 既知の性質

`TrackDefinition -> JSON -> TrackDefinition` は**ビット一致しない**。
現行の `serde_json` で f64 が 1 ULP ずれて往復することを実測で確認している
（`22.96100594190540178` -> `"22.961005941905402"` -> `22.96100594190539823`）。

トラックデータでは 1e-14 m の差であり物理的に無意味だが、
**「保存して読み直せばビット一致する」と仮定してはならない。**
アセット JSON が唯一の正であり実行時に再生成しないため、
PROJECT.md §7 の決定性契約（同一バイナリ・同一シードでビット一致）には影響しない。
